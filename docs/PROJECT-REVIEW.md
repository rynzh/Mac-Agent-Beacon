# GitHub 发布与成熟度评估

## 结论

适合以 **experimental / early access** 发布并邀请技术用户试用，暂不适合宣称“所有 Mac 一键稳定可用”。
它已有真实硬件验证、MIT 许可和第三方声明、测试、CI、可读源码以及默认不改键的安装流程。
核心差距不是 README 漂不漂亮，而是兼容性、发行可靠性和出现问题时用户能否自行恢复。

## 本次已补齐

- 新电脑单段安装入口：环境预检、临时下载、编译测试、安装程序、合并 hooks、登录自启。
- 明确把系统授权和 Codex 信任留给用户，拒绝 sudo / 覆盖已有安装。
- 安装失败保留诊断副本；尝试恢复没有被并发改动的配置。
- 独立服务管理，不再把后台运行与三键改键方案绑在一起。
- 服务归属检查、带空格路径测试、失败注册清理、重复安装保护。
- README 区分 Desktop、CLI、Claude 和通用事件支持，不把它们描述成相同能力。
- 准确说明 IPC 会接收完整快照再丢弃无关字段，而不是声称从未接触对话数据。

## 发布前优先事项

| 优先级 | 缺口 | 验收方向 |
| --- | --- | --- |
| P0 | 多机兼容性证据不足 | 至少多代 Apple Silicon / Intel（若宣称支持）、不同 macOS、未安装 Karabiner 的机器完成完整授权和人工审批测试 |
| P0 | Caps 原有灯光语义冲突 | 明确支持模式；验证正常 Caps 切换、输入法、重复 LED 写入不会误改键或丢状态 |
| P0 | 内部 Codex IPC / 数据库耦合 | 建立支持版本表；格式不兼容、首次连接失败时给出明确可见诊断，不让用户只看到“灯没反应” |
| P0 | 全新电脑验收仍缺 | 无旧缓存、无旧授权环境，从下载命令到授权、真实灯亮、人工等待、批准、完成、卸载逐项验收 |
| P1 | 无签名、公证和预编译发布 | 为目标架构构建 Release 附件，附校验和、签名 / 公证、版本信息；减少 CLT 安装门槛 |
| P1 | 无升级 / 回滚 / 旧映射迁移 | 保留 helper 授权身份、失败回滚、可恢复配置、幂等重复运行；不能只做覆盖复制 |
| P1 | 运行维护不足 | 日志轮转、磁盘写入频率 / CPU / 内存测量、睡眠唤醒、登录、强制退出和长期运行测试 |
| P1 | 失败状态管理简单 | 支持按任务确认 / 清除提醒；审视 12 小时过期策略和启动时旧状态恢复，不让过时记录控制灯 |
| P1 | CI 只覆盖单一 macOS runner | 补系统 / 架构矩阵、安装和卸载测试、失败回滚、模拟接口契约测试；固定外部 Action 版本摘要 |
| P2 | 新手诊断缺少友好界面 | 菜单栏状态、连接原因、测试按钮、直接打开授权位置；不需要用户读 JSON |
| P2 | 公开项目材料不足 | 演示 GIF / 视频、版本标签、CHANGELOG、支持矩阵、脱敏 issue 模板、安全报告渠道、英文 README |
| P2 | CLI / 多 Agent 能力不一致 | 为各 Agent 写独立适配与真实验收；不要用一个模糊的“支持所有 Agent”承诺替代 |

P0 不是说不能公开源码，而是说在完成之前不应按成熟产品宣传。

## 发行与供应链

当前下载命令执行 `main`，方便但不可复现；脚本本身和随后下载的源码还可能来自不同时间点。
发布稳定标签后，应让引导脚本和源码固定同一个版本，并对发布附件做校验。
预编译包不能仅“上传一个本机二进制”：需要明确构建过程、目标系统、签名、授权身份和回滚方式。
这些工作尚未完成，本次没有上传 Release、创建标签或 push。

## 本次验证的边界

完整测试结果：28 runs, 147 assertions, 0 failures, 0 errors。
另外用临时本地 Git 仓库演练了下载 / 克隆分支，再进行真实编译、安装和命令运行；
这验证安装器流程，但不是对尚未 push 的 GitHub 版本进行在线验收。

隔离安装演练使用真实编译和测试、包含空格的安装路径、安装后命令运行及重复安装拒绝。
服务单元测试使用隔离配置与模拟注册调用；没有替换维护者正在运行的 LaunchAgent。
审批信号和物理输出的原始验收边界见 `APPROVAL-VERIFICATION.md`。
因此，应把下一步资源优先放在“另一台干净 Mac 上完整走通”，而不是继续增加灯光模式。
